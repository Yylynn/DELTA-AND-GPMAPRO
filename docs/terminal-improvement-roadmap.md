# DELTA 时空交易终端完善方案与实施路线图

> 文档状态：评审稿  
> 编制日期：2026-08-24  
> 适用范围：`DELTA-Time-Space` 本地研究终端  
> 核心边界：只读取行情与公开研究数据，不读取交易账户、不生成订单、不自动交易

## 1. 执行摘要

DELTA 时空交易终端已经具备从数据获取、技术分析、证据聚合到策略验证的主要研究链路，并非一个仅展示 K 线的原型。当前系统包含富途 OpenD 不可变行情快照、本地 OHLCV 数据导入、DELTA/ITD、GPMAPRO、GPMA2/GPMAAPRO、信号解释、事件与组合回测、滚动样本外验证、市场风险雷达及新闻研究等能力。

成交量已经进入系统的多个层级：行情数据、主图成交量柱、RVOL 与均量监控、GPMAPRO 过滤条件、量价证据、决策确认和增量价值诊断。因此，系统并不缺少成交量功能；真正的缺口是当前成交量能力主要属于日线、周线和月线快照研究，尚未形成盘中持续采集、同时间段比较、自动告警、告警留痕和事后验证的完整监控闭环。

下一阶段不建议简单叠加大量成交量指标。应优先完成以下五项工作：

1. 修正 RVOL 历史基准，排除当前 bar 对自身基准的污染；
2. 建设盘中同分钟累计成交量与 RVOL；
3. 建立自选池扫描、异常告警、证据快照和结果复盘闭环；
4. 将成交量扩展为流动性、容量和市场冲击成本模型；
5. 用跨标的、跨市场状态和样本外数据验证成交量是否真正提供增量价值。

与此同时，系统还需处理新闻测试回归、GPMA2 富途逐 bar 对账、前端分包、自动化测试、版本基线和运行可观测性等工程问题。

## 2. 当前能力基线

### 2.1 数据与行情

- 支持富途 OpenD 历史 K 线快照；
- 快照保存来源、时间、复权方式、SDK 版本、SHA-256 和数据范围；
- 支持日线、周线和月线；
- 支持本地 OHLCV CSV 单文件及批量导入；
- 支持 A 股、港股、美股代码规范化；
- 包含字段合法性、重复日期、缺失记录、数据新鲜度及研究资格检查；
- 研究结果可绑定不可变快照，降低数据更新导致的结果漂移。

### 2.2 技术研究

- DELTA 时间窗口、ITD 时间结构和未来候选窗口；
- GPMAPRO 趋势、EMA 组、MACD、ATR、量能过滤、B/S 信号和背离；
- GPMA2/GPMAAPRO 本地计算与公式绘图；
- DELTA 与 GPMA 图层共享同一 OHLCV 快照和时间轴；
- 信号解释、条件阻塞原因及研究型仓位语言。

### 2.3 证据与决策

- 将 DELTA、趋势、信号、成交量、历史回测和新闻组织为结构化证据；
- 输出 BUY、WATCH、WAIT、RISK 等研究状态；
- 显示证据方向、强度、可信度、冲突和数据质量；
- 支持成交量确认与不利成交量证据；
- 支持确认项边际价值和跨标的稳健性诊断。

### 2.4 回测与验证

- 固定持有期事件收益；
- DELTA、GPMAPRO、方向一致组合及随机时点对照；
- 信号日收盘确认、下一交易日开盘成交；
- 双边固定成本、资金曲线、最大回撤、年化波动率和 Sharpe；
- 长仓、现金约束、等现金分配的组合回放；
- 滚动样本外窗口；
- 按信号、确认项、置信度、决策状态和年份分组；
- CSV 导出和研究准备度门槛。

### 2.5 风险与新闻

- VIX、VXN、VVIX、VIXY 等市场波动率观察；
- 市场技术信号与风险告警；
- 公司新闻、宏观新闻、来源健康状态和引用信息；
- 新闻因子快照与样本外验证框架；
- 未通过统计门槛时明确标记为未验证。

## 4. 成交量能力评估

### 4.1 已有能力

系统当前已经具备：

- OHLCV 中的原始成交量；
- K 线图底部成交量柱；
- 5/20 周期均量；
- `volume / MA5` 与 `volume / MA20`；
- VERY_LOW、LOW、NORMAL、HIGH、VERY_HIGH 分级；
- SPIKE 与 DRY_UP 异常分类；
- EXPANDING、STABLE、CONTRACTING 趋势；
- UP/DOWN 与高低成交量组合形成的量价上下文；
- GPMAPRO 的 `vol_ok` 与 `vol_strong`；
- 决策系统中的成交量确认、不利量价证据；
- 成交量确认的边际收益诊断。

### 4.2 当前能力边界

当前所谓“成交量追踪”实际是：

```text
用户拉取或选择行情快照
        ↓
读取日/周/月 OHLCV
        ↓
计算当前 bar 的均量、RVOL 与量价状态
        ↓
在页面展示并进入证据/决策
```

它尚不包括：

- 实时或准实时逐笔成交；
- 1 分钟/5 分钟持续订阅；
- 今日累计成交量曲线；
- 与历史相同交易分钟比较的盘中 RVOL；
- 盘前、正常交易时段和盘后分段统计；
- 主动买入量、主动卖出量或盘口订单流；
- 自选池后台扫描；
- 成交量异常自动告警和持久化；
- 告警后的收益、回撤和失效统计。

因此，当前模块应定义为“快照式成交量研究”，不能宣传为“实时成交量监控”。

## 5. 完善原则

### 5.1 研究因果性优先

任何时点的信号只能使用当时已经可获得的数据。日线信号若依赖收盘数据，最早只能在下一交易时段执行。盘中告警只能使用截至当前分钟的累计成交量和历史同期基准。

### 5.2 验证优先于指标数量

新增指标必须说明经济含义、参数来源、样本外表现和增量价值。不能因为图形直观或单一标的历史表现较好就提高决策权重。

### 5.3 数据与结果可复现

行情快照、配置版本、代码版本、运行参数、随机种子和输出结果应共同形成研究运行记录。

### 5.4 保持研究终端边界

本路线图不要求连接账户或自动下单。流动性、仓位和冲击成本功能用于研究与风险估算，不用于生成实际订单。

### 5.5 保守处理缺失和低样本

历史不足、基准不可用、交易时段不完整或数据异常时，应返回 `INSUFFICIENT_DATA` 或 `UNAVAILABLE`，而不是用少量样本输出精确状态。

## 6. 完整改进清单

### P0：正确性与可维护性

#### P0-1 修正 RVOL 基准

当前滚动均量包含当前 bar。建议改为仅使用此前已完成的 bar：

```text
RVOL20(t) = Volume(t) / Mean(Volume[t-20 ... t-1])
RVOL5(t)  = Volume(t) / Mean(Volume[t-5 ... t-1])
```

实施要求：

- 先 rolling，再 `shift(1)`；
- 5 日基准至少需要 5 个已完成 bar；
- 20 日基准至少需要 20 个已完成 bar；
- 样本不足时不做 NORMAL/HIGH 等正式分类；
- 保留旧算法结果兼容字段，或明确升级指标版本；
- 新增边界、首个有效日和极端量测试；
- 重新校准现有 0.60、0.85、1.20、1.80、2.00 阈值。

验收标准：

- 改变 `t+1` 及未来成交量不影响 `t` 的结果；
- 改变 `t` 的成交量只影响分子，不影响 `t` 的历史均量基准；
- 少于20个历史 bar 时明确显示数据不足；
- 日、周、月周期分别验证。

#### P0-2 修复当前失败测试

需要处理：

- 新闻源注册表已增加 `finnhub_company`、`sec_edgar`，测试仍使用旧集合；
- 新闻因子测试同时断言 `symbols_captured == 30` 和 `== 1`，存在明显预期冲突。

验收标准：后端全套测试零失败，测试预期与实际产品配置一致。

#### P0-3 建立版本基线

当前子项目存在大量修改和未跟踪文件。建议：

- 先确认哪些生成数据不应进入版本库；
- 补充 `.gitignore`；
- 将代码、配置、公式、测试和文档分组提交；
- 建立一个可以启动、构建并通过测试的基线 tag；
- 在研究结果中记录 Git commit。

#### P0-4 数据质量加强

增加以下检查：

- 零成交量和连续零成交量；
- 成交量异常尖峰与历史分位数；
- 缺失交易日和不完整周/月 bar；
- 拆股、合股前后的量价一致性；
- 复权价格与未复权成交量的解释；
- 不同市场成交量单位；
- 指数、ETF、股票成交量语义区别；
- 重复快照、时区和交易日边界。

### P1：成交量监控闭环

#### P1-1 盘中数据层

优先支持 1 分钟 K 线订阅或定时拉取，5 分钟由1分钟数据聚合。每条盘中记录至少包括：

- 市场、代码、交易日、交易时区；
- bar 开始和结束时间；
- OHLC；
- 单 bar 成交量；
- 当日累计成交量；
- 数据源和采集时间；
- 交易时段：盘前、正常、盘后；
- 完成状态：形成中或已完成。

第一阶段无需逐笔成交和 Level 2，先完成可靠的一分钟量能研究。

#### P1-2 同分钟累计 RVOL

盘中不能直接将当前累计量除以完整日均量。建议定义：

```text
Intraday RVOL(t, m)
= CurrentDayCumulativeVolume(t, m)
  / Mean(PriorSessionCumulativeVolume(t-k, m), k=1..20)
```

其中 `m` 是交易开始后的分钟序号。需要：

- 只使用此前完整交易日；
- 半日市、临时停牌和提前休市单独处理；
- 盘前、正常、盘后分别建曲线；
- 对历史同期分布同时计算中位数、P75、P90、P95；
- 至少有10个有效历史交易日才展示实验值，20日后才给正式状态。

#### P1-3 自选池扫描器

建立本地后台任务：

```text
OpenD 行情订阅/轮询
        ↓
分钟 bar 与累计量更新
        ↓
量能特征计算
        ↓
规则与冷却时间判断
        ↓
保存告警证据快照
        ↓
前端通知与历史复盘
```

扫描器必须有连接状态、最近成功时间、失败次数、重连状态和数据延迟指标。

#### P1-4 首批告警规则

建议从少量可解释规则开始：

| 规则 | 初始定义 | 用途 |
| --- | --- | --- |
| 盘中异常放量 | 同分钟累计 RVOL ≥ 2.0 | 发现成交活跃突变 |
| 放量突破 | 突破近期高点且 RVOL ≥ 1.5 | 趋势确认候选 |
| 放量下跌 | 当日跌幅达到阈值且 RVOL ≥ 1.5 | 风险提示 |
| 缩量回踩 | 上升结构中回撤且 RVOL ≤ 0.7 | 抛压减弱候选 |
| 量价背离 | 价格创新高而量能分位下降 | 趋势衰减预警 |
| 成交额异常 | 当前成交额超过历史同期 P95 | 跨价格水平比较 |

所有阈值均为待验证初始值，不能直接视为有效策略参数。

#### P1-5 告警持久化与去重

每条告警应保存：

- 唯一 ID、代码、市场和时间；
- 规则版本与配置版本；
- 触发值、阈值和历史基准；
- 当时可见的 OHLCV；
- 快照或数据哈希；
- DELTA/GPMAPRO/市场风险状态；
- 告警严重度和冷却时间；
- 后续1、5、10、20日收益和最大不利变动；
- 是否确认、失效或重复。

同一规则、同一标的在冷却窗口内不应重复刷屏，但数值继续恶化时可升级严重度。

#### P1-6 前端成交量中心

新增独立页面或总览区域：

- 自选池实时状态表；
- 当前累计成交量和同分钟历史曲线；
- RVOL 排名；
- 异常量、放量上涨、放量下跌、缩量回踩分类；
- 告警时间线；
- 点击告警定位到对应 K 线；
- 数据源、延迟、新鲜度和交易时段；
- 日线快照与盘中形成中数据明显区分。

### P1：流动性、容量与成本

#### P1-7 流动性指标

新增：

- 20/60日平均成交量；
- 20/60日平均成交额 ADV$；
- 成交额历史分位数；
- Amihud 非流动性指标；
- 价格跳空与成交额组合；
- 标的流动性等级。

#### P1-8 容量约束

组合研究应支持：

- 单笔交易金额占 ADV$ 的比例；
- 目标最大参与率；
- 按流动性限制最大研究仓位；
- 高换手策略的容量折减；
- 无法可靠成交时拒绝计算理想化收益。

初始保守规则可将单笔金额限制在 ADV$ 的 1% 以下，随后按市场和策略验证调整。

#### P1-9 成本模型升级

将固定 bps 扩展为：

```text
总成本 = 佣金 + 买卖价差 + 滑点 + 市场冲击
```

至少支持：

- 市场和资产类别成本模板；
- 固定成本与流动性成本两种模式；
- 根据参与率和波动率估算冲击；
- 乐观、基准、悲观三种成本情景；
- 在回测报告中显示毛收益、净收益和成本吞噬比例。

### P1：研究严谨性

#### P1-10 成交量增量价值验证

核心比较不是“带成交量的策略是否赚钱”，而是：

```text
相同基础信号 + 成交量确认
vs
相同基础信号 - 成交量确认
```

需要比较：

- 样本数和交易数；
- 平均值、中位数、胜率；
- 5/10/20日收益；
- 最大有利/不利变动；
- 成本后收益；
- 最大回撤和 Sharpe；
- 跨标的改善比例；
- 不同行情状态的一致性；
- 参数上下浮动20%的稳定性。

只有满足以下条件，成交量才可提高决策权重：

- 样本量达到预设门槛；
- 样本外结果为正；
- 多数合格标的方向一致；
- 至少两个主要市场状态有效；
- 成本后仍有改善；
- 不是依靠单一年份或少数极端事件。

#### P1-11 多重检验与假设登记

记录每个尝试过的成交量规则、参数和结果，避免只保存成功版本。规则数量较多时使用 FDR 或更保守的多重检验修正。正式验证前锁定主要假设、指标定义和验收门槛。

#### P1-12 市场状态分层

至少按以下状态报告结果：

- 多头趋势；
- 空头趋势；
- 横盘震荡；
- 高波动；
- 低波动；
- 流动性正常与流动性紧张。

不得仅使用总样本平均结果掩盖状态依赖。

### P2：产品与工程完善

#### P2-1 GPMA2 权威对账

完成本地 GPMA2/GPMAAPRO 输出与富途逐 bar 绘图结果的系统性对账，包括信号日期、图标、文字、价格坐标和重复抑制。未完成前继续显示来源状态和不确定性，不把本地等价重建描述为完全一致。

#### P2-2 前端性能与测试

- 按总览、风险雷达、回测、数据、新闻和设置页面懒加载；
- 拆分 Carbon、图表库和大型研究组件；
- 增加关键组件和交互测试；
- 覆盖加载、空数据、后端断开、超时和错误状态；
- 建立 bundle 大小预算。

#### P2-3 可观测性

增加本地运行状态页或结构化日志：

- OpenD 连接和版本；
- 行情最后成功时间；
- 当前订阅数量；
- 数据延迟；
- 后端任务队列；
- 新闻源健康状态；
- 最近失败和重试次数；
- 前后端版本和 Git commit；
- 磁盘数据量与保留策略。

#### P2-4 研究运行登记

每次重要回测保存：

- run ID；
- Git commit；
- 数据快照 ID/哈希；
- 公式和规则版本；
- 完整参数；
- 标的池；
- 起止日期；
- 成本模型；
- 随机种子；
- 输出指标与导出文件。

#### P2-5 风险与组合研究

在不连接账户的前提下增加：

- 波动率目标仓位；
- 单标的、行业和市场风险上限；
- 相关性聚类；
- 最大同时持仓；
- 回撤降风险规则；
- 压力场景；
- 信号拥挤和流动性压力。

## 7. 按难易程度分类

### 7.1 评估口径

难度不是单纯按代码行数判断，而是综合以下因素：

- 需要修改的前后端模块数量；
- 是否依赖新的行情数据；
- 是否涉及交易日历、时区、断线重连等边界情况；
- 是否会改变现有研究结果；
- 是否需要积累真实交易日数据；
- 是否需要样本外、跨标的和统计显著性验证；
- 出错后是否会产生错误研究结论。

以下工作量以一名熟悉当前项目的全栈量化开发者为参考，不包含等待真实市场数据积累的自然时间。

### 7.2 难度一级：简单，可立即完成

特点：改动范围有限、依赖少、验收明确，通常不改变系统架构。

| 工作项 | 预计开发量 | 主要内容 | 完成标准 |
| --- | ---: | --- | --- |
| 修复两项新闻测试 | 0.5天 | 同步新闻源集合；修正互相冲突的覆盖数量断言 | 后端全套测试零失败 |
| 整理 `.gitignore` | 0.5天 | 排除缓存、构建物、临时数据和不应提交的运行快照 | Git 状态只显示应纳入版本管理的文件 |
| 建立可运行版本基线 | 0.5至1天 | 分组提交代码、测试、配置和文档，建立基线 tag | 指定 commit 可启动、测试和构建 |
| 澄清成交量页面文案 | 0.5天 | 明确“快照成交量”与“盘中实时监控”的区别 | 页面不再产生实时性误解 |
| 增加零成交量检查 | 0.5至1天 | 检测单点零量、连续零量和全周期零量 | API 返回明确质量状态并有测试 |
| 增加基础运行元数据 | 1天 | 回测结果记录快照 ID、参数、运行时间和 Git commit | 导出结果可追溯到代码与数据版本 |
| 增加后端版本/连接状态 | 1天 | 在系统状态接口展示版本、OpenD 端点和最近成功时间 | 前端可以判断当前是否正常连接 |

建议优先完成这一组。它们可以快速降低回归、版本混乱和用户误解风险。

| 工作项 | 状态 | 实施结果 |
| --- | --- | --- |

### 7.3 难度二级：中等，适合短周期迭代

特点：需要修改核心计算或多个模块，但数据源和总体架构不需要重建。

| 工作项 | 预计开发量 | 难点 | 前置依赖 |
| --- | ---: | --- | --- |
| VOLUME_V2 滞后均量 | 1至2天 | 改变现有 RVOL 结果，需要兼容旧字段和补充边界测试 | 成交量定义评审 |
| RVOL warm-up 状态 | 0.5至1天 | 短历史不能继续输出看似精确的等级 | VOLUME_V2 |
| 日/周/月分别校准 | 2至4天 | 不同周期不能机械共用同一阈值 | VOLUME_V2、合格历史数据 |
| 成交量异常值与分位数检查 | 2至3天 | 区分真实放量、拆股和数据错误 | 基础质量检查 |
| ADV20/ADV60 与成交额分位数 | 1至2天 | 统一价格、成交量和市场单位 | VOLUME_V2 |
| 告警数据模型与本地持久化 | 2至4天 | 规则版本、证据快照、去重状态和结果字段设计 | 规则定义 |
| 告警查询和配置 API | 2至3天 | 过滤、分页、配置验证和兼容性 | 告警数据模型 |
| 前端页面按路由懒加载 | 1至3天 | 当前 `App.tsx` 较集中，需要避免状态和查询回归 | 前端构建基线 |
| 前端加载/空数据/错误测试 | 2至4天 | 需要补充测试框架与 API mock | 页面接口稳定 |
| 本地运行状态与结构化日志 | 2至4天 | 统一多个数据源和后台任务的状态 | 系统状态接口 |
| 固定成本情景 | 1至2天 | 输出乐观、基准、悲观三组净收益 | 现有组合回测 |

这一组可以形成第二个开发批次。其中 VOLUME_V2 虽然代码不复杂，但会改变历史结果，应按“中等”而不是“简单”处理。

### 7.4 难度三级：困难，需要跨模块设计

特点：需要新的数据链路、后台生命周期或较大范围的前后端协作，边界情况较多。

| 工作项 | 预计开发量 | 核心难点 | 主要风险 |
| --- | ---: | --- | --- |
| OpenD 一分钟行情采集 | 4至7天 | 订阅、轮询、时区、bar 完成状态、缓存和限额 | 重复 bar、漏数、连接中断 |
| 同分钟累计 RVOL | 4至7天 | 历史同期曲线、交易分钟索引、半日市和停牌 | 基准错位导致伪放量 |
| 自选池后台扫描器 | 5至8天 | 任务调度、并发、重连、状态恢复和资源限制 | 长期运行不稳定、重复扫描 |
| 告警去重、冷却和升级 | 3至5天 | 状态机和规则版本一致性 | 告警风暴或遗漏升级 |
| 盘中成交量中心页面 | 5至8天 | 排名、曲线、实时刷新、定位 K 线和错误降级 | 页面性能、状态不同步 |
| 告警后收益自动归因 | 4至7天 | 未来1/5/10/20日结果补全和样本截止处理 | 未完成样本被误计入 |
| GPMA2 富途逐 bar 对账 | 5至10天 | 富途权威输出获取、图形语义和逐 bar 差异定位 | 本地等价实现与源公式不一致 |
| 流动性参与率与仓位限制 | 3至6天 | ADV$、最大参与率和组合现金约束联合计算 | 容量假设过于理想化 |
| 市场冲击成本模型 | 5至10天 | 参与率、波动率、价差和资产类型联合校准 | 模型精确外观掩盖估计误差 |
| 组合相关性与风险约束 | 5至10天 | 动态相关性、行业暴露、同时持仓和回撤规则 | 参数过多、结果过拟合 |

这一组不宜全部并行。推荐先完成一分钟数据与同分钟 RVOL，再做扫描器和页面，最后处理容量及组合风险。

### 7.5 难度四级：复杂研究，需要数据积累

特点：开发代码只是其中一部分，主要难点在于真实数据覆盖、研究设计、统计验证和长期稳定性。

| 工作项 | 代码开发量 | 额外自然周期 | 难点 |
| --- | ---: | ---: | --- |
| 盘中 RVOL 阈值正式校准 | 3至5天 | 至少20个完整交易日 | 不同标的和交易时段的分布差异 |
| 成交量增量价值样本外验证 | 5至10天 | 视历史分钟数据覆盖而定 | 保持基础信号一致、控制多重检验 |
| 跨标的/跨市场状态验证 | 5至10天 | 可能需要数周补齐数据 | 牛熊、震荡和高低流动性分层样本不足 |
| 告警规则淘汰与晋级体系 | 4至7天 | 至少一个稳定观察周期 | 防止只保留历史表现最好的规则 |
| 动态市场冲击和容量校准 | 7至15天 | 需要可靠价差或成交数据 | 免费或基础行情不足以支持精细校准 |
| 逐笔成交、订单流或 Level 2 | 10至20天以上 | 取决于权限和数据许可 | 数据量、权限、语义、存储和回放复杂 |
| 长期运行稳定性验证 | 3至5天修复迭代 | 至少20个交易日 | 断线、休市、网络波动和进程重启 |

这一级不能用“功能已写完”作为完成标准。必须经过真实交易日采集、异常回放和样本外报告后才能宣布完成。

### 7.6 按难度安排的推荐顺序

#### 第一批：简单修复，约2至4个工作日

1. 修复新闻测试；
2. 整理版本库和 `.gitignore`；
3. 建立可运行基线；
4. 明确快照成交量文案；
5. 增加基础运行元数据和零量检查。

#### 第二批：核心正确性，约1至2周

1. 实现 VOLUME_V2；
2. 加入 warm-up 和日/周/月独立状态；
3. 加强异常值、拆股和周期完整性检查；
4. 增加 ADV$、成本情景和结构化运行状态；
5. 完成前端初步分包和错误状态测试。

#### 第三批：盘中 MVP，约3至5周

1. 一分钟行情采集；
2. 同分钟累计 RVOL；
3. AAPL、QQQ、SPY 三标的扫描原型；
4. 告警持久化、去重和冷却；
5. 盘中成交量中心；
6. 连续运行与断线恢复测试。

#### 第四批：研究验证，开发约2至4周，另需数据观察周期

1. 告警结果自动补全；
2. 有/无成交量确认的成对比较；
3. 跨标的、跨年份和市场状态验证；
4. 参数敏感性与多重检验；
5. 规则保留、降级或淘汰。

#### 第五批：高级风险与容量，约3至6周

1. 参与率和流动性仓位上限；
2. 市场冲击成本；
3. 组合相关性和风险约束；
4. GPMA2 权威对账；
5. 根据实际需要决定是否引入逐笔成交或 Level 2。

## 11. 总体验收标准

终端完善工作完成后，应满足：

1. 日线 RVOL 使用已完成历史 bar 作为基准；
2. 盘中 RVOL 使用历史相同分钟累计成交量；
3. 形成中 bar、已完成 bar 和日线快照清晰区分；
4. 每条告警可以追溯到数据、规则和代码版本；
5. 告警有去重、冷却、升级和恢复逻辑；
6. 断开 OpenD 时不显示伪实时状态；
7. 数据不足时明确拒绝给出精确判断；
8. 成交量规则经过样本外和跨标的验证；
9. 回测包含成本、流动性和容量约束；
10. 后端测试、前端测试和生产构建全部通过；
11. 新闻、GPMA2 等实验能力明确标记验证状态；
12. 系统继续保持不读账户、不下单的研究边界。

## 12. 建议的首个开发批次

建议第一批只做以下内容，避免一次扩张过多：

1. 创建 `VOLUME_V2`，修正滞后均量和 warm-up；
2. 补充零量、异常量、拆股和不完整周期质量检查；
3. 修复当前两项新闻测试；
4. 增加研究运行的 Git commit、快照 ID 和参数记录；
5. 设计一分钟成交量数据模型，但暂不加入复杂订单流；
6. 做一个仅包含 AAPL、QQQ、SPY 的盘中 RVOL 原型；
7. 连续采集并观察至少20个交易日，再决定告警阈值；
8. 使用历史分钟数据完成首轮无成交量/有成交量成对验证。

这个批次完成后，再决定是否扩展到完整自选池、更多市场和流动性成本模型。

## 13. 最终判断

DELTA 当前的主要问题不是缺少功能，而是部分功能之间还没有形成严格、可复现、可监控、可验证的闭环。成交量模块已经具备良好基础，最合理的演进方向是从“展示日线量能状态”升级为“持续追踪盘中量能、保存证据、验证预测价值并约束策略容量”。

只要优先保证因果性、样本外验证、成本模型和数据可追溯，终端就能从功能丰富的研究工作台进一步成长为可信度更高的量化研究平台，同时保持目前安全、清晰的不交易边界。
